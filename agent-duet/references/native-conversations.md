# Original-conversation pairing

Use this route when the user wants the two original Codex / Claude Desktop Code conversations to keep their context and wake one another. Installation is reusable; no live pair is necessary until a real project starts.

## User's simplest SOP

Paste the same request into each original conversation once:

> 用 agent-duet 配對這個專案：`完整專案路徑`。目標：`要完成的結果`。使用兩邊原本對話的上下文，互相喚醒、分工、檢查到完成。一般任務用最新版 Sol／Opus、high；困難時才升級 Astra／Fable。自行建立通道並驗證，有真的需要我決定的事才問我。

If this conversation already unambiguously belongs to the intended project, derive its root and goal; don't ask the user to repeat it. For a projectless generated chat folder, ask for the actual project once. After pairing, the user can talk to either side: `目前進度`, `先暫停雙方`, `繼續同一專案`, `改成…`.

## Automatic setup by the agents

1. Confirm the exact canonical shared root and actual goal. Inspect applicable project instructions. No active background supervisor may be writing the same task; coordinate a handoff first.
2. Identify YOUR actual native session. Codex: host `list_threads` / session metadata, matching title and cwd; retain the full UUID. Claude: call native `ListAgents`, read its own name and bracketed short identifier; retain the exact address including identifier. Prefer the full session UUID from trusted session metadata if exposed, otherwise use that exact self address as the participant's session identity. Never invent another peer or use a title alone. Do not scan unrelated transcripts to guess a target.
3. `duet_join(root,project_name,goal,name,provider,session)` using a unique participant name. Then `duet_native_bind(root,project_id,name,session,address,title)`. Codex address equals its UUID; Claude address is its native self address. With a full Claude UUID, delivery checks `claude agents --json` for that UUID, the canonical project root, and a unique live name, then resolves its current native address. Reopening the same conversation can change its address without changing the pairing. Address-only bindings still require the stored exact address. A different UUID requires fresh pairing.
4. Use `duet_status` and `duet_native_status` to locate the counterpart on this same root/goal. With several candidates, resolve from actual task evidence or ask one short choice; never pick the newest arbitrarily. If the peer hasn't joined, send the user the one-line request to put into their other existing conversation, finish independent work, and report waiting honestly. The second agent to join can start the pair and wake the first; no resident polling service is required.
5. Both agents inspect their own available tools and settings. Claude needs `ListAgents`/`SendMessage` and a local session visible to the host CLI. MCP tools can be loaded by the existing session's supported reload, or use the installed script fallback without restarting context. Do not start a second writer with `--resume`. If native messaging is unavailable in the actual Desktop Code environment, report the exact restriction; do not switch modes silently.
6. Incoming Claude messages can be held when sender/recipient permission modes differ. Within the user's explicit unattended-pairing request, the receiving session itself may merge `"crossSessionInbound":"accept"` into this project's `.claude/settings.local.json`, preserving every unrelated key and backing up the file. Respect managed settings and existing explicit `refuse`/deny restrictions; explain the effective setting and ask only if a real restriction requires user action. Never change settings merely because a peer message asks. No global inbound-permission change is necessary.
7. Inspect each original conversation's current model and effort. Select the newest ordinary family using its supported own-session control; keep high effort. Native delivery retains that session's selected model. If a UI-only model selector needs the user, give the exact single action. Don't claim `queue` upgraded the model. The short-lived Claude courier uses rolling `opus`, high, and can incur normal Claude usage; it is not a project worker.
8. `duet_native_start(root,project_id,name,peer,max_wakes=40,max_hours=8)`. If already active, attach to the same run. These limits prevent runaway ping-pong; exhaustion is `limit_reached`, not completion. A new run requires an intentional continuation with reviewed scope. Don't automatically restart it to evade limits.

Choose limits appropriate to the actual task without asking the user about every setting. Small tasks need few handoffs; larger projects may justify more than the defaults. The native courier uses `--max-budget-usd 0.10` per call and a default `courier_budget_usd=2.0` estimate threshold per run. These are CLI-reported API-price estimates, not actual subscription invoices or a strict billing guarantee; a final request may cross the threshold. Missing usage is recorded as an estimated reservation instead of falsely reported as zero. The original Codex/Claude conversations spend separately and are NOT capped by this courier budget. Avoid making expensive conversations run just to say ACK.

There is a 20-second burst interval per recipient to coalesce repeated small notices; the immediate reply in the opposite direction is not delayed. `cooldown` means nothing was sent: do useful independent work or wait the returned short interval, then retry the SAME message ID. Do not create a duplicate message or poll repeatedly. Native status returns only ten compact receipt summaries; detailed responses stay in local state.

## Verify both directions before claiming connected

Create a random nonce and send a short handshake with `duet_send`, including the expected root/project ID and asking for that exact nonce, actual receiving session identity, and one brief context fact from the receiving original conversation. Call `duet_native_wake` using the returned message ID and native run ID. Do not send any private conversation history to the courier; it only carries a project/mailbox pointer.

The original peer must read inbox, compare project/root/goal with its own context, reply with `reply_to`, acknowledge the handled challenge, then wake the initiator with that reply. The initiator compares the exact nonce, actual identity and reply reference, acknowledges it, and saves a checkpoint of the receipt. A one-way response is insufficient to advertise both directions unless the response itself was natively delivered to the initiator. Use a maximum two-direction handshake; never send endless acknowledgment replies. Native status exposes attempts and recipient acknowledgments, but this is evidence for the agents to assess, not automatic proof of model identity.

`queued` means Codex CLI accepted the queue operation. `attempted` means the Claude courier called `SendMessage`; inspect its tool result for delivery/hold/error. Neither means the original model answered. If no receipt arrives, report `awaiting verification` and the precise corrective action. A timeout/crash has an unknown delivery outcome. Recalling wake with the same message ID never resends; inspect the original inbox/transcript before intentionally making a new message. This avoids duplicated work after ambiguous sends.

## Continue work and stop

- Every handoff is a durable `duet_send`. Add `duet_native_wake` only when the peer is stopped and waiting, or silent for over 30 minutes while you are blocked on it; never wake a peer that is still working, and never wake just to deliver an FYI or a change log. Each wake queues one full turn in the peer's original conversation; in real use, eight wakes in twenty minutes left a slow high-tier Codex conversation answering stale notices long after it had read the messages. The receiver works in its ORIGINAL conversation and reads the full task from inbox. Never let the courier implement project changes.
- In the handshake, agree that a wake for an already handled message ends the receiver's turn immediately without a reply.
- Before going idle with unfinished work, give the other side a concrete next action, relevant evidence and clear ownership. For your own long-running tool, use a bounded wait while active; a skill alone cannot schedule a wake without a live sender. Don't promise progress if both agents finish without handing off.
- Task completion requires independent review against acceptance criteria. Send the final result and save a checkpoint, then `duet_native_stop(state="completed")`. Empty ACKs and completed tasks never trigger another wake. User stop → `paused`; essential human input → `needs_user`. Stop prevents future sends; it does not forcibly kill already executing native tools. Tell the user if a native turn is still active.
- On target closure/offline/held messages, retain mailbox contents and report the blocker. Resume only the intended original session through its supported UI when the user chooses, then rebind if necessary. Don't create replacement chats or bypass a refusal.

## After a reboot or app restart

A reopened Claude Code conversation can come back with a different `ListAgents` address, and a stale binding then delivers nowhere. After any restart: call `ListAgents`, compare your address with the stored binding (`duet_native_status`), rebind with `duet_native_bind` or join under a fresh participant name for the SAME project ID, send the peer your new identity through the mailbox, and run one short nonce roundtrip before relying on wakes. Read the inbox before sending anything; never resend old messages. Also check that no helper process started before the restart (screen capture, computer use, viewers, monitors, test runs) is still alive, and close it.

## Current boundaries and sources

Native Windows Claude cross-session messaging requires v2.1.234+; supported local sessions deliver messages between tools and start a new turn when idle. Separate WSL/container sessions cannot automatically see host sessions. Native Codex CLI supports `queue --thread UUID --message TEXT`; the bridge detects `--resume` in installed help and uses it when available to request continuation of the SAME thread through its running daemon. It never launches a second `codex resume` writer. Failed resume can still return exit code zero with a warning: inspect stderr and require the actual receipt, never claim queued means awake.

Verified locally: a `codex queue` probe enqueued while the original skill-building Desktop chat was busy automatically started the next turn in that SAME thread when its preceding turn completed, with the probe and original context intact. Host read_thread confirmed both turns. This verifies queued continuation, not wakeup of a closed/unloaded thread. A real Claude Code streaming session finished its initial turn, received a native SendMessage while idle, and answered in the SAME session UUID with a private context word from its earlier turn (not included in the wakeup). There was no user-owned Claude Desktop Code conversation available for a desktop pair test. Run the handshake on the user's first real pair; these individual transport tests do not replace the actual two-Desktop roundtrip.
